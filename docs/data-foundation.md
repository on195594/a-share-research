# 数据层治理方案

研究库用公司标识贯通候选、报告与记分样本，用稳定的报告编号关联账户归因。业务状态的归属见[系统架构](../ARCHITECTURE.md)。

## 公司标识与查询

`company_key` 是六位 ASCII 数字字符串。研究任务、报告、价格参考、扫描事件、订阅和披露检查表从原始 `code` 生成该列。写入接受六位代码或带 `.SH`、`.SZ`、`.BJ` 的九位代码，生成列的非空约束拒绝全角数字、空白和无效后缀。`code` 留作存证和展示，报告、预测与快照保留其原文和哈希。

内部查询在 SQL 之前用 `stock_codes.normalize_key` 归一化入参，支持六位和带后缀的代码。首尾空白的容错仅在入参边界生效。数据源适配层自行处理交易所代码及行业成分中的特殊标识，例如 `T00018.SH`。

## 表布局与关系

SQLite 读取位于大字段之后的小列时可能遍历溢出页。`runs` 的 `request`、`identity`、`material`，`reports.body`，以及 `calls` 的 `response`、`prompt` 位于表尾。常用查询可以直接取元数据，无需拆表和联接。

| 关系 | 查找与核验 |
|---|---|
| 任务与父报告 | `runs.parent_report_id` 从请求中的同名字段生成，非空行建索引。`is_feedback` 来自请求中的 `feedback` 是否非空。父报告与子任务公司不同是完整性错误。手工删除父报告会产生断链，巡检列入 `dangling_parent_reports`，读取侧标记基线缺失。 |
| 任务与批次 | `runs.batch_id` 从完整的 `batch-<正整数>-<公司代码>` 生成，批号无前导零，公司段为同一六位代码或其规范后缀形式。按此列联接 `batches` 判定批次是否存在、是否属于自动月批。孤立任务列入 `orphan_batch_runs`。 |
| 任务、报告与账户归因 | `runs.id`、`reports.id` 使用 `AUTOINCREMENT`，删除最新行后其编号仍保留在序列中。恢复备份时须另行核对高水位。 |

## 记分样本

`db.RESEARCH_ORIGINAL` 选择 `kind='research'`、`replay_of IS NULL`、非纠错的任务。`db.FORMAL_REPORT` 还要求 `passed=1` 和任务状态 `done`。批次复用正式报告时另按时效过滤，并排除围绕原报告作答的接续报告。

冻结记分按各自定义选样。`validation.source()` 按请求中 `feedback` 的真值判断纠错，按问题是否等于批次研究问题区分批次与主动研究。按通过报告取样的查询不额外要求任务状态为 `done`。统一这些条件须另开记分版本。[判断验证与记分](judgment-validation.md)

## 7 验收与治理规则

1. 带公司代码的新表须有 `company_key`，跨表公司比较只用它。表间关系用列表示。大字段放表尾，在其后追加高频读取的列须配索引或重建表。
2. 复用适用的样本常量。涉及选样的变更在同一份真实数据副本上比对新旧样本编号，再用已通过报告的失败、运行中和纠错变体验证冻结语义。真实库里恰好没有某类样本时，编号一致仍不足以证明选样条件一致。
3. 迁移在事务内执行并支持重入。用 `table_xinfo` 检查生成列。重建后核对索引、触发器、外键、序列和 `integrity_check`，对按设计原样保留的非生成列按列名逐行比对，包含冻结 JSON 和哈希。检查重建中断能回滚，新建库可启动，两个连接并发启动只执行一次迁移。新库首次并发切 WAL 曾出现锁竞争，验收需覆盖空库启动。
4. 在生产副本上用实际回退镜像验证读写、完整性与业务兼容。不兼容的迁移须单独设计回退。应用与数据库的可用组合以[实施计划的回退基线](implementation-plan.md#当前部署)为准。
5. 从旧备份恢复数据库会丢失备份之后的写入，由所有者决定。停服后先记录现库 `sqlite_sequence` 的任务、报告高水位，以及账户事件引用的最大报告编号。恢复并完成所需迁移后，开放写入前把两个序列分别抬到相应高水位，核对账本引用的报告都存在且对应正确。高水位无法可信重建时，须先完成归因核对。
