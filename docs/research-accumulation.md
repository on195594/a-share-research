# 研究积累与降噪方案

更新：2026-11-05。本文件维护研究积累的设计和验收口径，依据[路线图](roadmap.md)和 [PRODUCT.md](../PRODUCT.md)。K1–K6 的既有设计见第 3 节，K7 受控演进续作见第 6 节；部署与复盘进度统一见[实施计划](implementation-plan.md#工作包与状态)，K2/K3 逐次记录见 `git show 52d1eec:docs/implementation-plan.md`「K2/K3 推进记录」。

## 1 背景与诊断

用户在 2026-10-27 提出三个问题：研究过的公司越来越多，会不会拖慢页面？会不会产生噪音、干扰投资决策？项目是否只是在熵增，没有积累投资经验？

以下是实施前的诊断，数据来自 10-21 至 10-27 的生产库只读查询：19 份报告来自同一初筛批次，其余多数是开发验收。表中代码行为与缺口属于当时基线，不描述当前实现；长期数字是估算。

| 编号 | 问题 | 依据 | 影响 |
|---|---|---|---|
| P1 | **目前没有已证实的性能瓶颈；增长较快的是磁盘** | 首页 `latest_reports()` 走 `reports_by_code` 索引，但仍要关联 `runs`、扫描历史并排序，`SELECT r.*` 还会返回完整正文（平均约 18KB，以 UTF-8 字节计，下同）。库约 49MB，其中 `calls` 占 73%：探索阶段每轮都把累计消息全量存一次，平均每次约 140KB，摊下来每次研究接近 1MB。PDF 缓存 282MB。现有约 10 份部署前整库备份。磁盘已用 83%，剩 17G | 假设每月 40 次研究，主库每年约增长 0.5GB。页面在当前规模下没有问题，更大规模还没有实测。部署备份没有保留策略 |
| P2 | **首页把初筛产物和自己的研究混在一起**（使用数据） | 首页「研究过的公司」共 27 家，其中 19 家只有初筛深挖报告（`runs.request_id LIKE 'batch-%'`） | 每月最多新增约 20 家，大部分会是批次产物，具体比例取决于和主动研究重复的程度。批次页本来就列着这些公司 |
| P3 | **三档结论缺乏区分度，原因未查明**（使用数据） | 36 份通过复核的报告中，30 份是「需要谨慎」；去掉批次报告后，主动研究的 17 份里仍有 12 份。可能的成因有：批次的固定问题偏重风险；`RULES` 没有定义三档的划分标准；复核只追查「漏掉的重大风险」；「需要谨慎」不影响入选观察表。10-27 的校准只重放了冻结材料上的成文步骤，没有覆盖探索阶段 | 列表只显示结论词，起不到筛选作用。本批不改结论设计（见第 5 节），只在列表中提供其他区分信息 |
| P4 | **旧报告没有过期提示，`period` 口径也前后不一**（使用数据） | 当时列表只显示「资料至某期」，`period` 取首份文档和 `T.*` 财务行的最大期间；但早期报告 5、6、7 的 `period` 是 2025-12-31，而它们的财务表已包含 2026-06-30 | 三季报 10-31 截止，多数报告即将过期，却仍以同样的权重留在首页；直接用 `period` 判断会误标早期报告 |
| P5 | **同一家公司重研时不接续上次的判断**（代码行为） | [`_research_context()`](../a_share_research/research.py) 只带入追问时指定的父报告和纠错通过的报告。现有几次不带父报告的重研是开发验收，还算不上真实的跨期复查 | 三季报披露后，「这次财报是否改变了判断」会成为高频场景（路线图第 1 节的目标场景），而每次重研都从零开始 |
| P6 | **判断没有和事后发生的事实对账**（代码行为） | 只有冻结批次有前瞻收益；报告里没有可证伪的检查点，下一次研究无从核对上次关注的事项 | 积累的是文本，不是经过对照的经验 |
| P7 | **跨公司经验沉淀依赖手动纠错** | 「纠错 → `methods` → 跨公司检索」现有 2 条方法。路线图第 4 节要求经验先经过「真实失败 → 定位根因 → 候选 → 验证」才能采用，这个门槛是有意设置的 | 日常研究不会自然产生改进；但绕过这个门槛，又会带入未经验证的泛化 |

本方案以接续研究（P5）和事后归因（P6、P7）形成积累，并处理首页分组和过期提示。

## 2 设计原则

- 不新建知识库、向量库、笔记或「已阅/关注」状态（路线图第 6 节、PRODUCT.md）。积累串联已有报告、财务表、行情与改进记录；K7 的运行记录在服务内可见，仓库外仅保留开发评估附件。
- 不改写、不删除历史报告；对照差值只读计算，新判断与方法变更保留独立版本。
- 来源分组、过期判断、财务差值全部由确定性程序完成，不放宽 `check()` 来接受上下文中的数字。
- 研究结论只判断「是否值得继续研究」（[项目契约](project-contract.md)第 2 节），不是买卖评级。对账以基本面事实为主；判断和事实不一致时，必须先归因，再决定是否改进。
- 不营造交易紧迫感。收益展示与记分以判断验证及初筛实验为准，不从单份报告事后涨跌宣称研究有效。

## 3 方案

### K1 首页降噪与过期提示（针对 P1 前半、P2、P4）

**来源分组**：来源按每份报告自身来判断，不沿追问链回溯。一家公司只要有至少一份「非批次、非重放」的报告，就算「我的研究」，在首页列出。判断条件是 `COALESCE(u.request_id, '') NOT LIKE 'batch-%'` 并且 `replay_of IS NULL`；CLI 任务的 `request_id` 可能为 NULL。对批次报告追问或纠错产生的报告属于主动研究，所以这家公司也会进入「我的研究」。

只被初筛深挖过的公司不在首页逐家列出，只显示一行「初筛深挖过 N 家，见各批次」并链到 `/batches`。首页展示该公司最新一份非重放报告，批次产生的也算，这样和公司页一致；如果来自批次，加注「来自初筛」。

**过期提示**：
- 只读推导一个「财务数据覆盖期」：取 `period` 与 `body.table` 中 `T.*` 行的最大期间，两者取大。这样不改写旧报告，也能纠正早期 `period` 偏旧的问题。
- 再取截至今天已过法定截止日的最新报告期，称为「常规应披露期」。截止日为：一季报 4-30、半年报 8-31、三季报 10-31、年报次年 4-30。
- 覆盖期早于常规应披露期时，提示「资料未覆盖常规应披露的 2026 三季报」，否则不提示。

用词只说「未覆盖」，不说已确认该公司发布了新公告。覆盖期是财务数据的期间，不代表相应的定期报告正文已被完整阅读。提前披露、延期披露、新上市公司都无法只靠日期识别，这是有意接受的限制。为了不制造新的噪音，只设这一种状态，不在披露窗口内提前给弱提示。

**查询瘦身**：`latest_reports()` 只返回列表字段及用于判断检查点入口的文字，不在首页展示第一条检查点。SQLite 提取 JSON 时仍要读取正文，当前不增冗余列或分页。

**10-29 阅读续作**：首页主动公司列表用原生折叠，先列已有核查请求的待处理状态；有事项时折叠新研究表单，无事项或发生输入错误时展开。来源分组和覆盖提示保留，普通检查点只链到全文，不单列第一条暗示最高优先级。事项仅来自明确父报告的反馈请求，以原报告/位置/文本去重，组内最新结果通过才退出。失败核查的专用重试沿用原父报告及反馈；普通研究不代替这条关联。不创建已读状态，不根据日历、生成时间或普通风险推断事件。新证据与到期提醒的数据依赖尚未具备，范围、限量与无数据降级统一见[升级方案 7.7](investment-upgrade.md#77-步骤-2首页事项与报告阅读)，本页不另建路线图。

### K2 接续研究与检查点（针对 P5、P6，并为 P3 提供列表上的区分信息）

**检查点**：报告新增 `checkpoints` 段，格式为 `[{"text": ..., "cites": [...]}]`，写 1–3 条「下一期披露中应观察的事项和方向，以及出现什么情况会削弱当前判断」。

检查点是条件性判断，核验口径如下：
- 基期事实照常核验：主体、期间、单位、数字都必须被所引出处支持。出处可以是原文、`T.*` 或 `C.*`。观察阈值要么来自出处，要么由程序计算得出，不能凭空写。
- 复核时不要求原文证明未来的方向，只检查基期事实，以及条件和判断是否相关。这个例外只适用于条件句，写进 `RULES` 和 `review()` 的说明。
- 报告未通过复核时，检查点不进入 `facts` 回退展示。

**接续上下文**：用户没有指定父报告、且不是批次、纠错或重放任务时，`execute()` 通过 `_prior_report()` 选取同一家公司最近一份「通过复核、非重放、非纠错」的报告，研究内容只带它的 `risks`、`checkpoints`、`period` 和 `market_date`，**不带 `verdict` 和 `summary`**，统一标为「待复核的旧风险与检查点（不是事实来源，也不是完整的取证清单）」。

批次任务不自动接续，这样跨公司比较的输入（`_report_digest()` 读取的 `risks`、`answer`）保持原有含义。

**关闭规则（防止旧议程递归积累）**：
- `risks` 段的职责不变：按重要性只列出当前仍可能推翻判断的风险，新披露中的重大反证优先。
- 旧风险和旧检查点在本期的状态（仍存在、已缓解、已证伪、无法判断，附本次材料的出处）写在 `answer` 末尾的几条里。没有用户问题时，自动补一个问题：「相对上次研究（资料至某期），哪些风险与检查点发生了变化？」这个问题在页面上可见。
- 下一次接续只读取最近一份通过复核、非重放、非核查报告的当前 `risks` 和 `checkpoints`，不递归带入旧 `answer`。若新报告已把关闭事项移出当前议程，该项就不再继承。是否应移除、是否正确移除，按本次出处与后续 K3 记录核查；逐项状态自 K5 起记录在 `prior_status`，此前的报告程序不解析回答文字。
- 原研究正文不新增 `changes` 字段。

#### 公司研究进展（2026-11-03 已退役）

曾尝试在独立研究完成后按需生成并复核附属比较记录（`progress.py` / `progress_import.py`）；因生产首对样本（万华 41→44）复核未通过且跨期对比已由 K2 接续回答与下述 `reading.comparison()` 确定性对照承担，已于 2026-11-03 从应用代码退役，数据库表保留只读兼容。原设计细节见 `git show c2d212f:docs/research-accumulation.md`。

**确定性差值（只给人看）**：报告页和公司页的「前后变化对照」由 `reading.comparison()` 对明确的父报告/接续关系计算，缺失关联不按时间配对；**不放进模型上下文，也不能被正文引用**。模型本来就能看到本次材料中的多期财务表，没有必要另开一条证据通路。口径如下：
- **新增覆盖期**：本次财务表有、上次没有的期间。如果新增的只是历史比较期（例如补进了上年同期），注明「补齐比较期」，不称为新披露。
- **数据修订**：同一行、同一期间，新旧数值不同。
- **估值快照**：两次 `market_date` 的 PE、PB、股息率。
- 不对不同期间的累计值做差；百分比指标的差写成「个百分点」。旧报告缺少的字段显示「上次未采集」，不当作零。
- 只有 `T.*` 财务行与估值快照参与对照，「本次未记录」「口径不一致」也只就这些行判断：`C.*` 是各报告自行编号的计算，同业行不属于本公司，均不列入（11-04，此前每次对照都把估值行、`C.*` 行列为未记录或未比较）。新表不再保留的旧期间按期间列出，不逐项列指标。估值快照随交易日变动，不计入「项修订」，也不使面板默认展开。

报告版本对照与公司经营时间序列分别处理；后者口径见[升级方案第 7 节](investment-upgrade.md#7-投资论证与可比阅读续作)。K2 对照使用独立的代码和数据基线，位置及执行协议见实施计划（`git show 52d1eec:docs/implementation-plan.md`「K2/K3 推进记录」）。

**阅读入口**（11-04，11-05 随 K5 调整）：「相对上次改变了什么」以接续报告的回答和旧议程状态为准，程序差值只核对数字口径。公司页卡片在最新报告为接续研究时，优先链到旧议程状态。K5 之前的接续报告没有这一段，回答完整展开，不折叠末尾的状态文字，程序不解析这些文字。

**列表展示**：K1 的首页保留最新报告的检查点入口，点击阅读全部检查点；没有结构化日期时，不将它标为到期事项。

**兼容**：重放沿用快照冻结的上下文；纠错和事实回退使用同一段落位置语义。接续报告被纠错时不再加载新议程，但上下文带上它所接续的旧议程（`prior_agenda`），因为 `prior_status` 的 `ref` 指旧报告的条目，不是本报告的同名位置。`research-v1` 保持新增字段兼容，按[项目契约](project-contract.md#6-版本验证与文档维护)验证 Skills 消费端。

### K3 归因复盘（针对 P6、P7；既有基线）

以下为既有个案复盘方式；自动运行、核查采用与系统内读取由第 6 节 K7 接续，旧操作不是 K7 的人工前置条件。

**复盘的对象是归因，不是对错。** 判断和后来的事实不一致时，可能是合理更新（风险条件没有发生、环境变了），也可能是当时的取证、计算或推理出了错。只有后者才需要改进。

**记录格式**：仓库外证据目录中的一份 Markdown，每个案例一节，包含：
1. 当时的判断，以及当时可得的证据（报告 ID）；
2. 后来的事实（接续报告 ID，以及它在 `answer` 中给出的、带出处的状态说明）；
3. 归因：合理更新 / 取证遗漏 / 计算错误 / 推理错误 / 无法判断；
4. 最小改进候选（提示词、工具、数据、方法），或者不改的理由；
5. 采用后的验证结果，或者拒绝的原因。

允许不产生 `methods`。只有归因为研究错误、且改进能跨公司复用时，才发起纠错，走现有的方法核查通道；改代码或提示词则走正常的开发闭环（路线图第 4 节）。

**节奏**：K2 的首次真实接续就做第一次复盘，不用等价格窗口。之后每季度财报季结束时，Agent 汇总这一季的接续报告做一次。证据来源优先用接续报告中已核查的状态说明；检查点涉及分部、单价、订单等 `T.*` 没有的指标时，标为「需补读披露」或「无法判断」，不把「表里没有」当成「没有兑现」。

**真实关闭观察**：正常研究出现有证据支持的关闭事项时，记录其判断依据，再观察后续接续是否正确移除该项。没有真实样本就保留“未覆盖”，不改写历史结果，不为填满这一分支重复研究。该观察不作为 K2 收尾或其他工作包的前置条件。

**价格观察**：口径统一由[判断验证方案](judgment-validation.md)维护；2026-10-31 前旧限制仅留 Git 历史，不在此重复。

### 定位：可记分的判断账本（2026-11-05 所有者确认）

项目积累的方向是“可记分的投研判断账本”，知识库是它的读取面，不是独立的产品或存储。所有者明确优先级是赚钱，因此先建能检验判断的状态账本，再建读取面。

11-05 生产库只读统计：15 天 103 份报告、39 家公司；每份平均约 200KB，其中 92% 是财务表和序列，分析文字约 6KB；方法 2 条，8 次检索记录都来自同一份源报告（不代表实际采用）；接续 11 份，其中只有 2 份的财务覆盖期确实前进；126 条预测的目标期都是 2026 年报。当前还没有一条积累经过结果检验。

- **值得积累**：可引用的证据；判断、结果与归因。
- **不当事实来源**：AI 写的历史结论和综述。接续研究不带旧结论防锚定、事实只来自当次资料的边界不变。
- **公司事实不追求存全**：可从披露和行情重取；要保存的是当时知道什么、判断了什么、后来发生了什么。

### K5 议程状态账本（针对 P6、P7；服务避开大亏与复盘改进）

**问题**：接续报告把旧风险和检查点的状态写在 `answer` 文字里，程序不解析，所以统计不了“旧风险有多少真的发生”，H1 的复盘只能逐篇读。另外现有状态词里“仍存在”同时覆盖“条件还在”和“不利结果已经发生”，后者恰恰是避坑最需要区分的。

**字段**：接续报告（`material.extra.prior` 存在）新增 `prior_status`，覆盖 `prior.risks` 和 `prior.checkpoints` 的每一项，且每项恰好一次：

```json
{"prior_status": [{"ref": "risks[0]", "status": "已发生", "text": "本期状态说明", "cites": [出处]}]}
```

`ref` 是旧报告的章节位置。报告不可改写，所以 `prior.report_id + ref` 就是稳定身份，不新增 ID。

| 章节 | 状态 | 含义 |
|---|---|---|
| risks | 已发生 | 该风险描述的不利结果已在本次资料中体现（可以是部分体现，`text` 写明范围） |
| risks | 仍存在 | 风险条件还在，不利结果尚未体现 |
| risks | 已缓解 | 风险条件减弱，但未消失 |
| risks | 已证伪 | 本次证据显示该风险不成立或已解除 |
| checkpoints | 已触发 | 检查点所述削弱判断的情况已出现 |
| checkpoints | 未触发 | 相应披露已覆盖，削弱判断的情况没有出现 |
| checkpoints | 未到期 | 相应披露尚未发生 |
| 两者 | 无法判断 | 证据不足；`text` 写明缺什么，不当作“未发生” |

**校验**（`check()` 确定性执行，复核员核语义）：

- 有 `prior` 时必须提供；没有 `prior` 时不接受此字段。
- `ref` 集合与 `prior` 的条目一一对应，缺项、重复、越界都报可操作错误（列出缺哪几项）；状态须属于该章节的取值。旧议程为空时必须接受 `prior_status: []`（这是 `check()` 通用“章节不能为空”的例外），缺失的旧章节按零项处理。历史快照沿用冻结的字符串列表及其下标。
- `text`、`cites` 与正文同样核对数字和引文。只有“无法判断”“未到期”可以没有出处，这是放宽，配互变测试证明其他状态缺出处、或伪造数字仍被拦下。
- 到期不做机械判定：事件型检查点（如合同交付）没有统一财务到期日，财务覆盖期前进不代表它已到期。“未到期”的理由由复核员核对；财务覆盖期只用于 V5 样本筛选。
- 复核提示新增一条：核查状态是否被本次出处支持，`已发生`/`仍存在` 的区分是否合理；旧报告文字不是证据。区分三种“无法判断”：资料已有证据却未用，复核员记 `claim`，阻断；可补读但还没读，记 `question`，进入修复，仍未解决则作为具名缺口随报告发布（规则同 `answer[i]`，写入 `open_questions` 和 gaps，不静默过关）；确实无法取得的，`text` 写明缺口即可。“已有证据却报未知”是语义判断，确定性测试测不了，靠 V5 公开每份的无法判断占比和真实样本抽查发现。

**与回答的分工**：逐项状态从 `answer` 末尾移到 `prior_status`，`answer` 只回答问题并概括变化，避免同一内容写两遍。旧报告不回填，继续从 `answer` 阅读。这对读取 `answer` 逐项状态的消费者是语义变化，新报告应改读 `prior_status`。

**流程接入**（都须改代码，不能假定现有条目机制自动覆盖）：

- 成文与发布：`prompts.PRIOR`、`research.published()` 白名单。
- 校验与复核：`checking.check()`；`reviewing.target_exists()` 接受 `prior_status[i]`；`research.OPEN_QUESTION_WHERE`。
- 修复：`research.REPAIR_SECTIONS`、`merge_repair_patch()` 的位置正则（现只接受 `[a-z]+`，须允许下划线）；补丁条目必须保留 `ref`、`status`，合并后重新校验一一对应。
- 失败回退：`research._verified_facts()` 须识别该位置并排除该段，不能因此清空其他事实，与检查点一致。
- 位置反馈：`service` 的合法位置正则、`research._research_context()` 的待核查内容、纠错页标题映射、README 的合法位置合同。
- 读取：`reading.evidence_ledger()` 计入该段引文，否则引文从 `answer` 移走后证据计数偏低；compact 的 `continuation` 增加 `previous_risks`（原只有 `previous_checkpoints`），`report` 增加 `prior`、`prior_status`，使 `risks[i]` 能就地解释。接续不用于追问，所以 `continuation.parent_report_id` 与 `prior.report_id` 一致。

不改完整性巡检：它按整份正文和材料哈希核对，不依赖章节白名单。

**不做谱系**：旧风险改写后在新报告里是新条目，程序不追踪“同一风险”的跨期身份。每个条目只在下一期被判定一次，统计按“条目 × 期”计，不需要语义匹配。

**展示**：报告页在回答之后列“旧议程状态”，每项显示旧条目原文（读取旧报告，链到原位置）、状态文字标签、说明，引文可展开；公司页接续入口优先跳到这一段。
**记分**：见[判断验证 V5](judgment-validation.md#v5-议程状态记分2026-11-05)。

### K6 跨公司内容检索（读取面）

**问题**：研究库和 `/api/reports` 原来只能按公司查，无法回答“哪些公司出现过集采风险”这类跨公司问题。外部 Agent 也只能逐家读。精简读取已由 `GET /api/reports/{id}?compact=true` 提供，不重复建设。

**方案**：不建表、不建索引，直接查现有报告 JSON（与 `research_methods` 的取舍一致）。依据是 11-05 在生产库实测：

- 用多路径 `json_extract` 只取正文文字：生产副本（104 份报告）每家最新一份约 60ms，含历史约 100ms。
- FTS5 的 `unicode61` 不切分中文，`trigram` 查不了“集采”这样的两字词，都不适合中文短词。
- 派生表还要处理同步与重建，当前规模没有收益。升级条件：生产库实测 P95 超过 1 秒再评估。

**接口**：`reading.search_items()`，`GET /api/search?q=&code=&section=&history=&page=`（API 鉴权）；网页在研究库增加“搜研究内容”。

- **匹配**：按空白切成 1–5 个词，全部出现（AND）；按字面匹配，`%`、`_` 不是通配符；总长不超过 100 字。
- **范围**：通过复核、非重放、非纠错的研究报告；章节为 risks、checkpoints、answer、business、financial、stance、prior_status。纠错报告的 `methods` 继续走既有检索（含退役逻辑），不进入本接口。
- **默认只查每家公司最新一份**，避免重跑造成近似重复：先按 `company_card` 的资格和排序确定每家的报告，再展开章节并匹配关键词。旧报告含某词而最新报告不含时不返回。`history=true` 才跳过“选最新”这一步。不复用研究库的 `latest_reports()`，它是先过滤后选最新，且包含失败和纠错报告。
- **结果**：`report_id`、`code`、`name`、`created_at`、`period`、`location`（如 `risks[2]`）、`text`，每页 20 条，按报告从新到旧。不返回结论词和事后表现；结果带覆盖期，是否过期由读者判断。
- **边界**：检索结果是待核查线索。**本批不接入 worker 研究员工具**，研究输入不变。

## 6 受控演进方案：让积累服务于赚钱

### K7 目标与边界

本节是 K3 的自动化续作设计，不是已实现能力；实施状态只见[实施计划](implementation-plan.md#工作包与状态)。目标是 **AI 自动发现问题、核查和采用方法，人类可观测、可反馈，不当流程管理员**。正常运行无需人类定期触发、抄录记录或逐条批准付费调用与方法。

不另建学习平台、知识库、向量库、多 Agent 流水线或常驻服务，不做自动交易。授权、安全与发布边界以 [AGENTS.md](../AGENTS.md) 为准，不在本节增加审批门禁。

**不等条件（所有者 2026-11-06 决定）**：K7 每一步只有固定日期和到期默认动作，不设“等真实失败出现”“跑通后再看”这类进入条件。AI 主动从现有报告、缺口与复核记录中找候选、做对照，不等问题自己出现。到期未交付就公开标为逾期并说明原因；方案不合适就改方案，不能延期了事。唯一不能提前的是收益标签成熟和 H1 单次正式检验，它们限制结论时点，不限制读数和复盘工程。

K7 属于维护与能力建设，不以它宣称投资效果。运行指标是所有者每周介入次数、首轮复核通过率、失败到修复的时长、缺口被后续方法填补的比例；投资效果仍只看[判断验证](judgment-validation.md)的 V/H1 记分。

### 6.1 两个反馈循环

| 循环 | 过程 | 能支持的结论 |
|---|---|---|
| 快循环：单次任务至数周 | 真实缺陷 → 根因 → 最小候选 → 受影响真实案例与正常案例 → 核查 → 自动采用、拒绝或暂缓 → 观察及撤回 | 改善可靠性、任务效果和成本；不证明收益 |
| 慢循环：原记分成熟窗口 | 冻结判断与对照 → 等待结果 → 分解筛选、研究、等待与执行表现 → 形成资源调整建议 | 在原协议与样本限制内评价投资效果；不自动调仓 |

复用[判断验证](judgment-validation.md)与[初筛实验](screening-experiment.md)，不重定义冻结阈值、样本资格、入场规则或 H1 单次正式检验。Q20−指数看初筛，Q5−Q20看规则集中，L5−Q5看深挖增量；H1 避坑、V1 财务预测优于基线都不等于做多赚钱。模拟不冒充真实账户收益，观察性差额不冒充因果证明；按公司、期间和批次说明相关性，重叠窗口不当独立样本。

研究成本区分实际费用、共享订阅分摊和人工估计；金额未知就报可得用量。粗略盈亏平衡门槛“年研究成本 ÷ 服务资金规模”只作参考，资金规模须由账户 owner 提供，缺失不阻断本项目；交易和研究费用不重复扣除。不读取或复制账户库，不补写事前决策。账户贡献未核实就明确标未知。

### 6.2 自动触发与运行保护

优先处理已有订阅和候选中的四类问题：新披露可能推翻原命题；研究与简单规则的重要分歧；影响判断的同材料不稳定；报告缺口跨公司反复出现（主动挖掘，不依赖失败）。新披露触发复用 A4 扫描，并以[论点卡证伪条件](investment-advisor.md#5-a2-论点卡research)的机械判定作确定性前置。先使用已有证据，必要时窄范围补证，再决定完整研究。不增加全市场 LLM 扫描，不因接近估值门槛反复采样直到得到理想答案。自然语言条件无法机械判断时由 Agent 核查，仍缺证据则标未知。

复用 worker 与任务持久化：
- 新披露、报告/复核完成、用户反馈登记事件；内部低频到期检查补扫遗漏与成熟读数变化。具体周期和水位在实现时确定并展示，不新建 cron。
- 先程序去重和检测变化，再调用 AI。成熟数据复用评分函数或已有外部结果，不执行宿主 CLI；外部结果未更新时显示滞后，不能假装已检查。
- 幂等身份覆盖来源事件、原报告/方法版本和问题类型；重启可恢复，失败有限重试与退避。自身诊断结果不能无条件再次触发相同诊断。
- 普通研究、扫描和批次步骤都空闲后才执行诊断（worker 串行，诊断走空闲分支）；诊断在空闲时逐个生成，不长期占队列，以免阻塞发布空闲检查。这是防失控，不是正常研究深度或付费审批限制。
- 无新事件不重复调用模型；用户可手动触发，但不是运行前提。

### 6.3 同系统可见，按用途隔离

使用同一生产服务、队列和数据库；独立评估库只用于开发验证，不是用户观察入口。当前 `validation.load_reports/load_forecasts/load_agenda` 排除重放，却可能纳入普通 research 诊断，故 **用途隔离与可观测读取必须在自动入口启用前完成**：

1. 用途存于 `runs.kind`（`research` / `price` / `diagnostic`，重放沿用 `replay_of`），来源、父任务存于 `request`，不需迁移；只有不经 HTTP 的 `service.submit_diagnostic` 能写诊断，模型与用户反馈不能自行改用途。读取一律显式过滤 `kind='research'`，所以新增用途默认不算正式研究。历史数据按原语义兼容，不重新筛选已有实验。
2. 诊断保存完整证据，但不替代最新正式报告、不推进正式覆盖期/检查点、不成为接续事实基线、不影响“今日已研究”或初筛正式选报。真实错误通过原纠错/接续机制生成关联的新版本，不能将事后诊断伪装为事前预测。
3. 逐项覆盖 V0–V5、排序/初筛、首次预测去重、报告搜索/API、最新报告和方法写入入口。集中定义用途判定，消费者显式使用；在原口径上排除新增诊断，不改成“所有记分只读批次”，不更改 H1。
4. 默认投资报告查询不混入诊断；任务/改进查询能找到诊断及其来源。诊断取证只产生候选，不能隐式写入生效方法。

字段优先复用 runs/request、报告附加信息和方法版本；不足时增加最小结构，不预建通用状态机。数据库迁移仍按原授权处理；这不是日常任务审批。

### 6.4 方法核查、记录与开发边界

候选可来自日常研究、成熟结果或反馈，但必须先归因再验证。候选生成与采用核查是分开的步骤/调用：核查读取原始证据、基线和真实案例结果，不只相信候选自评；程序检查出处、计算、关联及版本。证据不足自动拒绝或暂缓，不形成待人审批队列。共享模型可能有共同偏差，“独立步骤”不等于统计独立或已证明有效。

通过后沿用并扩展现有方法通道，自动采用、替换或撤下。运行身份记录 `methods_sha256`，因为方法变化不改变应用哈希；新采用的方法只从下一批次生效，在途批次不换方法，H1 复盘可按方法集分层说明。方法只影响研究启发，不修改硬校验、工具权限、投资政策或账户动作。事实仍须重新取证。代码/提示词问题形成可见开发事项，由开发 Agent 按常设授权处理；研究 worker 不获得宿主权限，当前也不假定常驻开发 Agent 会无人值守修代码。

系统自动持久化以下内容并供 Web/API 同源读取，仓库外文件仅留开发评估附件：

| 记录 | 最小内容 |
|---|---|
| 归因 | 候选 ID、原报告/位置、来源事件、数据截止时点、根因、服务的赚钱环节或维护性质 |
| 候选与验收 | 基线/候选身份、最小差异、适用范围、事前约定的真实案例/指标/阻断条件/运行次数 |
| 结果 | 包括失败在内的尝试、回归、成本、采用/拒绝/暂缓原因、版本、撤回关联 |
| 实际采用 | 方法 ID、报告位置、证据；区分独立 AI 核查确认、模型声称、未知，不等于收益贡献 |

保留 `methods_used` 的“检索召回”语义，不能由召回列表自动生成实际采用；旧报告缺字段表示未知，不回填。尽量保留未用于挑选候选的真实正常案例；不足时结论只限已测案例，后续自然样本补观察。不以采用次数、方法数量或改动数考核进化。

K7b 的最小执行协议复用诊断根任务的 `request/identity` 与 `calls`：来源集合按正式报告 ID 和正文哈希去重，规划可自主读取冻结报告的已存官方页与程序表格，独立步骤核查归因和判据后再入队案例。每个候选固定两家受影响及一家正常公司、每家每组一次；基线与候选从相同完整材料快照开始，继续探索而非仅重写正文。材料与方法目录的起点均留哈希，候选只多一条待验证方法，传入方式与正式采用相同。初版结论只支持这些案例，不能校准成功概率。

控制器在空闲时逐阶段推进，每次只登记一个子诊断；等待阶段不伪装成运行中的研究。阶段异常保留调用，一小时后最多重试一次，超过恢复上限暂缓；案例交付失败保留失败、不为采用追加采样。只有所有事前判据、无回退及依据核验通过，且受影响案例中的实际采用经独立核查确认，方法才生效。旧实验的拒绝可按原记录哈希及真实诊断任务登记为历史，导入入口不能采用方法。自动规划须读取已有拒绝／暂缓原因，不以更换名称重复已失败候选。

### 6.5 人类查看和反馈

在现有任务/研究页面提供研究改进入口与同源 API，不建设独立仪表盘。默认呈现重要变化：问题、判断影响、处理动作、当前状态与原因、关联报告、费用/用量及证据链接。诊断使用明确用途标签，不与正式投资报告混淆；完整事件按需展开，无变化显示最近检查时点，不制造待办。

用户可从报告或改进项反馈错误、遗漏、无帮助，补充文字，停用方法或暂停诊断。反馈自动关联原任务并核查，不直接成为事实或指令。暂停阻止后续诊断调度，运行中任务在安全边界结束，结果保留。明确要求保持停用的方法只有用户可解除，不能被相同候选自动恢复。

普通失败自动处理，不要求逐条确认。超出既有授权、无法恢复的故障、影响已采用方法的重要反证需突出提示。站内可见性不等于对外通知授权。用户不提供反馈也能完成闭环；不要求人类维护样本、写复盘或选择每个候选。

### 6.6 升级、停止与验收

模型与方法改动尽量隔离验证，按 AGENTS 的影响范围选择真实案例或评估集。固定材料重放须说明覆盖探索还是仅成文阶段；受训练数据泄漏影响，不能用于证明历史 alpha。少量同材料重复只作稳定性诊断，不能校准概率、按多数票交易或自动生成“不判别带”。

历史判断不变，生产可升级。每次实质版本变化保留身份及影响范围；版本分层只作诊断，不替换原冻结主分析。重大新策略另行前瞻登记，旧版成功不自动背书新版。不无限双轨：旧判断等待标签；尚未生成的冻结试验若依赖退役版本，记录偏离或未完成，由 owner 决定是否继续，不能事后改尺子。撤回沿用既有方法核查或正常发布机制，不删除证据。

以下为 K7 的验收内容；日期与状态只在[实施计划里程碑表](implementation-plan.md#k7-里程碑)维护，到期默认动作是交付或公开标逾期并改方案：

| 步骤 | 验收 |
|---|---|
| K7a 运行/读取契约 | 全部用途消费者与历史兼容明确；互变测试逐处钉住过滤；方法集进入运行身份；worker 空闲才跑诊断 |
| K7b 主动方法闭环 | 从现有缺口挖掘候选（首轮不依赖失败）→归因→真实受影响及正常案例对照→独立核查→自动采用/拒绝；无人审批，全链 Web/API 可见，原正式读数与最新报告不变 |
| 月批保护 | 不切换 worker、不发布（切换会使 screening 批次失败）；按实施计划清单验收 12-01 月批，其失败进入 K7b 输入 |
| 披露触发与证伪机械化 | 复用 A4，预测、`add_trigger` 与可机械判定的检查点在披露后自动判定并触发诊断；业绩预告季前上线 |
| K7c 持续运行与反馈 | 无变化不重复调用，重启不重复采用，失败退避，普通研究优先；反馈自动核查，暂停/停用有效；分歧与不稳定两类触发上线；真实页面和 API 按 AGENTS 验证 |
| K7d 成熟结果读数 | 沿原协议读数，区分筛选/深挖/等待/账户执行，说明相关性与成本，给出保持、收缩或有限扩张建议；未成熟的只作描述，不宣称收益 |

正确性、安全修复不以短期收益验收。候选无效果、重复补证无增量或维护负担超过价值时，可停止该候选/自动化投入，保留原研究与必要检查。成熟结果长期未见深挖增量且成本明显时提出收缩建议：预算决策不必等待科学证明，但不能据此自动停止冻结试验、调仓或宣称因果否定。

常设授权内调用和方法采用自动执行；改变授权、投资政策或风险承担仍由原 owner 决定。研究规模建议用成熟证据与成本支持，不增加逐任务审批。账户可评估性、风险承受力及资金规模未知时，不阻断研究内纠错，也不构成跨项目访问授权。
