更新：2026-10-27。**状态：经 AGY 与 Codex 两轮对抗审查；K1、K2 已实现并本机验收（未上线），K2 接续对照待三季报披露后完成。** 本机验收：11 份冻结材料重放 10/11 首次通过（长江电力纠错材料复核未过一次，补跑 2/2 通过且结论同基线），结论与基线 10/11 一致；万华化学正常案例与东方电缆连续两次接续通过；招商银行仍拒绝。证据在 `~/.local/share/a-share-research-evaluations/accumulation-k2-20261027/`。 依据[路线图](roadmap.md)第 1、4、6 节和 [PRODUCT.md](../PRODUCT.md)。审查记录见第 6 节；以后的部署记录统一记在[实施计划](implementation-plan.md)。

## 1 背景与诊断

用户在 2026-10-27 提出三个问题：研究过的公司越来越多，会不会拖慢页面？会不会产生噪音、干扰投资决策？项目是否只是在熵增，没有积累投资经验？

下面的数字来自生产库只读查询。数据只覆盖 10-21 至 10-27 这 6 天：19 份报告来自 10-24 的同一个初筛批次，其余多数是开发验收时的真实运行。所以每条问题都注明依据来自使用数据还是代码行为，长期数字一律当作假设估算。

| 编号 | 问题 | 依据 | 影响 |
|---|---|---|---|
| P1 | **目前没有已证实的性能瓶颈；增长较快的是磁盘** | 首页 `latest_reports()` 走 `reports_by_code` 索引，但仍要关联 `runs`、扫描历史并排序，`SELECT r.*` 还会返回完整正文（平均约 18KB，以 UTF-8 字节计，下同）。库约 49MB，其中 `calls` 占 73%：探索阶段每轮都把累计消息全量存一次，平均每次约 140KB，摊下来每次研究接近 1MB。PDF 缓存 282MB。现有约 10 份部署前整库备份。磁盘已用 83%，剩 17G | 假设每月 40 次研究，主库每年约增长 0.5GB。页面在当前规模下没有问题，更大规模还没有实测。部署备份没有保留策略 |
| P2 | **首页把初筛产物和自己的研究混在一起**（使用数据） | 首页「研究过的公司」共 27 家，其中 19 家只有初筛深挖报告（`runs.request_id LIKE 'batch-%'`） | 每月最多新增约 20 家，大部分会是批次产物，具体比例取决于和主动研究重复的程度。批次页本来就列着这些公司 |
| P3 | **三档结论缺乏区分度，原因未查明**（使用数据） | 36 份通过复核的报告中，30 份是「需要谨慎」；去掉批次报告后，主动研究的 17 份里仍有 12 份。可能的成因有：批次的固定问题偏重风险；`RULES` 没有定义三档的划分标准；复核只追查「漏掉的重大风险」；「需要谨慎」不影响入选观察表。10-27 的校准只重放了冻结材料上的成文步骤，没有覆盖探索阶段 | 列表只显示结论词，起不到筛选作用。本批不改结论设计（见第 5 节），只在列表中提供其他区分信息 |
| P4 | **旧报告没有过期提示，`period` 口径也前后不一**（使用数据） | 列表只显示「资料至某期」。按当前代码，`period` 取首份文档和 `T.*` 财务行的最大期间；但早期报告 5、6、7 的 `period` 是 2025-12-31，而它们的财务表已包含 2026-06-30 | 三季报 10-31 截止，多数报告即将过期，却仍以同样的权重留在首页；直接用 `period` 判断会误标早期报告 |
| P5 | **同一家公司重研时不接续上次的判断**（代码行为） | [`_research_context()`](../a_share_research/research.py) 只带入追问时指定的父报告和纠错通过的报告。现有几次不带父报告的重研是开发验收，还算不上真实的跨期复查 | 三季报披露后，「这次财报是否改变了判断」会成为高频场景（路线图第 1 节的目标场景），而每次重研都从零开始 |
| P6 | **判断没有和事后发生的事实对账**（代码行为） | 只有冻结批次有前瞻收益；报告里没有可证伪的检查点，下一次研究无从核对上次关注的事项 | 积累的是文本，不是经过对照的经验 |
| P7 | **跨公司经验沉淀依赖手动纠错** | 「纠错 → `methods` → 跨公司检索」现有 2 条方法。路线图第 4 节要求经验先经过「真实失败 → 定位根因 → 候选 → 验证」才能采用，这个门槛是有意设置的 | 日常研究不会自然产生改进；但绕过这个门槛，又会带入未经验证的泛化 |

熵增的根因是：每次研究的输出不进入下一次研究（P5），也没有和后来的事实对账，并找出差异的原因（P6、P7）。P2、P3、P4 是表面症状。

## 2 设计原则

- 不新建知识库、向量库、笔记或「已阅/关注」状态（路线图第 6 节、PRODUCT.md）。积累只靠串联已有的报告、财务表、行情和仓库外的复盘记录。
- 不改写、不删除历史报告；派生信息只读计算。
- 来源分组、过期判断、财务差值全部由确定性程序完成，不放宽 `check()` 来接受上下文中的数字。
- 研究结论只判断「是否值得继续研究」（[项目契约](project-contract.md)第 2 节），不是买卖评级。对账以基本面事实为主；判断和事实不一致时，必须先归因，再决定是否改进。
- 不营造交易紧迫感，任何页面都不显示研究后的涨跌。

## 3 方案

### K1 首页降噪与过期提示（针对 P1 前半、P2、P4）

**来源分组**：来源按每份报告自身来判断，不沿追问链回溯。一家公司只要有至少一份「非批次、非重放」的报告，就算「我的研究」，在首页列出。判断条件是 `COALESCE(u.request_id, '') NOT LIKE 'batch-%'` 并且 `replay_of IS NULL`；CLI 任务的 `request_id` 可能为 NULL。对批次报告追问或纠错产生的报告属于主动研究，所以这家公司也会进入「我的研究」。

只被初筛深挖过的公司不在首页逐家列出，只显示一行「初筛深挖过 N 家，见各批次」并链到 `/batches`。首页展示该公司最新一份非重放报告，批次产生的也算，这样和公司页一致；如果来自批次，加注「来自初筛」。

**过期提示**：
- 只读推导一个「财务数据覆盖期」：取 `period` 与 `body.table` 中 `T.*` 行的最大期间，两者取大。这样不改写旧报告，也能纠正早期 `period` 偏旧的问题。
- 再取截至今天已过法定截止日的最新报告期，称为「常规应披露期」。截止日为：一季报 4-30、半年报 8-31、三季报 10-31、年报次年 4-30。
- 覆盖期早于常规应披露期时，提示「资料未覆盖常规应披露的 2026 三季报」，否则不提示。

用词只说「未覆盖」，不说已确认该公司发布了新公告。覆盖期是财务数据的期间，不代表相应的定期报告正文已被完整阅读。提前披露、延期披露、新上市公司都无法只靠日期识别，这是有意接受的限制。为了不制造新的噪音，只设这一种状态，不在披露窗口内提前给弱提示。

**查询瘦身**：`latest_reports()` 不再返回完整正文，只提取列表所需字段（K2 之后会多一个第一条检查点）。SQLite 提取 JSON 字段时仍要读取正文，这在当前规模下可以接受，不为此新增冗余列。暂不分页。

**涉及**：`web.py`（`latest_reports`、`home_page`）、`templates/home.html`、覆盖期与过期规则函数及其测试。

### K2 接续研究与检查点（针对 P5、P6，并为 P3 提供列表上的区分信息）

**检查点**：报告新增 `checkpoints` 段，格式为 `[{"text": ..., "cites": [...]}]`，写 1–3 条「下一期披露中应观察的事项和方向，以及出现什么情况会削弱当前判断」。

检查点是条件性判断，核验口径如下：
- 基期事实照常核验：主体、期间、单位、数字都必须被所引出处支持。出处可以是原文、`T.*` 或 `C.*`。观察阈值要么来自出处，要么由程序计算得出，不能凭空写。
- 复核时不要求原文证明未来的方向，只检查基期事实，以及条件和判断是否相关。这个例外只适用于条件句，写进 `RULES` 和 `review()` 的说明。
- 报告未通过复核时，检查点不进入 `facts` 回退展示。

**接续上下文**：用户没有指定父报告、而且不是批次任务时，`_research_context()` 额外带入同一家公司最近一份「通过复核、非重放、非纠错」的报告，只带它的 `risks`、`checkpoints`、`period` 和 `market_date`，**不带 `verdict` 和 `summary`**，统一标为「待复核的旧风险与检查点（不是事实来源，也不是完整的取证清单）」。

批次任务不自动接续，这样跨公司比较的输入（`_report_digest()` 读取的 `risks`、`answer`）保持原有含义。

**关闭规则（防止旧议程递归积累）**：
- `risks` 段的职责不变：按重要性只列出当前仍可能推翻判断的风险，新披露中的重大反证优先。
- 旧风险和旧检查点在本期的状态（仍存在、已缓解、已证伪、无法判断，附本次材料的出处）写在 `answer` 末尾的几条里。没有用户问题时，自动补一个问题：「相对上次研究（资料至某期），哪些风险与检查点发生了变化？」这个问题在页面上可见。
- 下一次接续只会带入上一份报告当前的 `risks` 和 `checkpoints`，已关闭的事项留在 `answer` 里，不会再被继承。
- 不新增 `changes` 字段。

不带旧结论只能减少显式锚定，旧议程仍可能占用探索注意力，这一点由验收检验，不靠规则担保。

**确定性差值（只给人看）**：公司页最新报告的上方显示「自上次研究以来」的程序结果，**不放进模型上下文，也不能被正文引用**。模型本来就能看到本次材料中的多期财务表，没有必要另开一条证据通路。口径如下：
- **新增覆盖期**：本次财务表有、上次没有的期间。如果新增的只是历史比较期（例如补进了上年同期），注明「补齐比较期」，不称为新披露。
- **数据修订**：同一行、同一期间，新旧数值不同。
- **估值快照**：两次 `market_date` 的 PE、PB、股息率，注明「估值快照变化，不是收益」。
- 不对不同期间的累计值做差；百分比指标的差写成「个百分点」。旧报告缺少的字段显示「上次未采集」，不当作零。

**列表展示**：K1 的首页在结论词旁边展示最新报告的第一条检查点。

**涉及**（逐处列出，避免漏改）：
- `research.py`：`SCHEMA`、`output_schema()`（检查点，以及接续时 `answer` 的要求）、`RULES`、`SECTIONS` 的使用处、`check()`、`review()` 的说明、`repair()`、`_verified_facts()` 的位置正则（不认识的位置会让整份 `facts` 被丢弃）、`_research_context()` 的查询与字段、`execute()`（自动补问题、批次不接续、组装 `body`）
- 重放：快照里冻结的 `context` 保持原样；接续要求以快照中是否有旧报告为准
- `service.py`：纠错位置正则（不加 `checkpoints` 会返回 422）
- `web.py`：纠错位置标签、公司页差值块（只读计算）
- `templates/report.html`、`stock.html`、`home.html`
- API research-v1 信封：只新增字段，按[项目契约](project-contract.md)第 6 节验证 Skills 消费端

### K3 归因复盘（针对 P6、P7）

**复盘的对象是归因，不是对错。** 判断和后来的事实不一致时，可能是合理更新（风险条件没有发生、环境变了），也可能是当时的取证、计算或推理出了错。只有后者才需要改进。

**记录格式**：仓库外证据目录中的一份 Markdown，每个案例一节，包含：
1. 当时的判断，以及当时可得的证据（报告 ID）；
2. 后来的事实（接续报告 ID，以及它在 `answer` 中给出的、带出处的状态说明）；
3. 归因：合理更新 / 取证遗漏 / 计算错误 / 推理错误 / 无法判断；
4. 最小改进候选（提示词、工具、数据、方法），或者不改的理由；
5. 采用后的验证结果，或者拒绝的原因。

允许不产生 `methods`。只有归因为研究错误、且改进能跨公司复用时，才发起纠错，走现有的方法核查通道；改代码或提示词则走正常的开发闭环（路线图第 4 节）。

**节奏**：K2 的首次真实接续就做第一次复盘，不用等价格窗口。之后每季度财报季结束时，Agent 汇总这一季的接续报告做一次。证据来源优先用接续报告中已核查的状态说明；检查点涉及分部、单价、订单等 `T.*` 没有的指标时，标为「需补读披露」或「无法判断」，不把「表里没有」当成「没有兑现」。

**价格观察**（可选、辅助，2027-04 之后）：如果做，起点是报告完成后的第一个完整交易日收盘，个股（复权）和全收益基准用同一区间，只看 6、12 个月；主动研究和批次分开列，在各自来源内按同一公司同一自然月去重；**不按结论档位汇总**，也不用于评价研究质量。到时用一个只读 CLI 计算，不建表、不做页面。

### K4 存储保留（针对 P1 后半）

- 部署备份：每次经授权清理时，只保留最近 3 份。删除生产数据目录中的文件，**每次都需要当次授权**。
- `calls` 与 PDF 不清理：`calls.identity` 用于报告运行身份，PDF 是引文来源。把探索阶段改成增量记录会改变审计记录的结构，按当前增速一年内没有磁盘压力，**本批不改**；磁盘余量低于 10G 时再评估。

## 4 分阶段与验收

| 阶段 | 交付 | 验收 |
|---|---|---|
| K1 | 来源分组、覆盖期与过期提示、查询瘦身 | 确定性测试的输入取自真实报告，必须包含报告 5、6、7（`period` 偏旧）、一份批次报告、一份追问报告，以及年报与一季报同为 4-30 截止、三季报跨年这两种日期边界。生产库里还没有 `request_id` 为 NULL、或批次与主动研究交叉的报告，这两类边界用真实评估产物的行补足。本机开发实例接生产库副本，在 390×844 尺寸走一遍首页、公司页、批次页；只重建 web |
| K2 | 检查点、接续上下文与关闭规则、公司页差值 | ① **基础契约**：对 `calibration-20261027/` 的 11 份冻结材料各重放一次，确认检查点格式、核验与复核通过率没有回退；银行（600036）真实提交一次，确认仍被拒绝。② **接续对照**：三季报披露后，从「最新主动报告期 ≤ 半年报、且三季报已披露」的公司中选 2 家（当前符合条件的有东方电缆、长江电力、贵州茅台、华东医药、工业富联）。开跑前，先从三季报原文列出每家 3–5 条必须发现的事实，作为预设核对表。两组都在同一份生产库快照的独立副本上运行：基线组用当前代码（不接续），候选组用新代码（接续固定的旧报告 ID），因此不会互相污染。比较两组对核对表的覆盖情况，以及旧风险状态说明的出处。③ **生命周期**：在候选组的副本上，对其中一家再接续一次，检查新检查点的继承与关闭，以及已关闭事项不会被再次带入。④ **确定性检查**：在真实产物上检查检查点出处、修复后重新核验、失败时回退排除检查点、旧报告缺字段时的显示、差值口径（含「补齐比较期」）。⑤ 正常案例：1 家没有旧报告的公司。⑥ Skills 端读一次含检查点的报告；手机走一遍报告页和公司页。⑦ 用上述接续结果完成第一次 K3 复盘 |
| K3 | 复盘记录格式与季度节奏 | 首次复盘随 K2 验收一起完成；可选的价格 CLI 首次运行时，抽 3 份报告与 TuShare 原始数据逐项核对 |
| K4 | 部署流程文档写入保留规则 | 下次授权清理前列出要删除的文件，经确认后执行；完整性巡检通过 |

顺序是 K1 → K2（含首次 K3 复盘）→ K4 → 可选的价格观察。K1 改动小、不碰研究契约，可以先上线；K2 等三季报披露完再验收。每个阶段达到验收即停止扩展。

## 5 本批不做

| 不做 | 原因 |
|---|---|
| 独立知识库、向量库、笔记、已阅或关注状态 | 路线图第 6 节、PRODUCT.md 明确排除 |
| 修改三档结论的定义或提示词 | 原因未查明（见 P3）。改动会同时影响批次「可选」规则和 Skills 端的解释，需要单独立项，并且评估要覆盖探索阶段 |
| 按结论档位统计股价胜率，或在任何页面显示研究后涨跌 | 结论不是买卖评级；单个批次的样本处在同一时间截面，汇总会被误读为预测力 |
| 新增 `changes` 字段；把差值放进模型可引用的证据 | 分别用 `answer` 状态说明、给人看的程序结果承载，少开一条证据通路 |
| 自动从日常研究生成 `methods` | 绕过路线图第 4 节的归因与核查；改由 K3 归因后再决定 |
| 用人为构造的旧报告做反事实锚定测试 | AGENTS.md 规定不造合成数据；改用预设核对表加真实案例 |
