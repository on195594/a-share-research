# 研究积累与降噪方案

更新：2026-10-27。**状态：方案已经过 AGY 对抗审查并修订，未实施。** 依据[路线图](roadmap.md)第 1、4、6 节和 [PRODUCT.md](../PRODUCT.md)。审查记录见第 6 节；以后的部署记录统一记在[实施计划](implementation-plan.md)。

## 1 背景与诊断

用户在 2026-10-27 提出三个问题：研究过的公司越来越多，会不会拖慢页面？会不会产生噪音、干扰投资决策？项目是否只是在熵增，没有积累投资经验？

下面的数字来自生产库只读查询。数据只覆盖 10-21 至 10-27 这 6 天：19 份报告来自 10-24 的同一个初筛批次，其余多数是开发验收时的真实运行。所以下表把问题分成两类：一类有使用数据作证，另一类只能从代码行为推出。

| 编号 | 问题 | 依据 | 影响 |
|---|---|---|---|
| P1 | **页面性能目前不是瓶颈，真正在增长的是磁盘** | 首页 `latest_reports()` 走 `reports_by_code` 索引并关联 `runs`，`SELECT r.*` 会读出约 12KB 的完整正文。库 48MB，其中 `calls` 占 73%：探索阶段每轮都把累计的消息全量存一次，平均每次 77KB，每次研究约 0.8MB。PDF 缓存 282MB。现有约 10 份部署前整库备份，加主库约 140MB。磁盘已用 83%，剩 17G | 按每月约 40 次研究计，主库每年约增长 0.4GB，几千家之内页面仍是毫秒级。备份没有保留策略，是增长最快的部分 |
| P2 | **首页把初筛产物和自己的研究混在一起**（有使用数据） | 首页「研究过的公司」共 27 家，其中 19 家只有初筛深挖报告（`runs.request_id LIKE 'batch-%'`） | 每月自动增加约 20 家，一年后首页约八成是批次产物。批次页本来就列着这些公司，首页再列一遍是重复 |
| P3 | **三档结论缺乏区分度，原因未查明**（有使用数据） | 36 份通过复核的报告中，30 份「需要谨慎」。扣掉批次后，主动研究的 17 份里仍有 12 份是「需要谨慎」。批次固定问题偏重风险，`RULES` 没有定义三档的划分标准，复核只追查「漏掉的重大风险」，而「需要谨慎」不影响入选观察表。这些都可能让「需要谨慎」成为最安全的选择。10-27 的校准只在冻结材料上重放了成文，没有覆盖探索阶段，也没有解释原因 | 列表只显示结论词，起不到筛选作用。这个问题本批不改结论设计（见第 5 节），只在列表中提供别的区分信息 |
| P4 | **旧报告没有过期提示**（有使用数据） | 列表只显示「资料至某期」。这里的 `period` 取已读定期报告和程序财务表的最新期间，也就是报告用到的最新财务数据，不对照法定披露截止日 | 三季报 10-31 截止，多数报告即将过期，却仍以同样的权重留在首页 |
| P5 | **同一家公司重研时不接续上次的判断**（由代码推出） | [`_research_context()`](../a_share_research/research.py) 只带入追问时指定的父报告和纠错通过的报告。现有几次不带父报告的重研（长江电力、茅台）是开发验收，不是真实的跨期复查，所以使用数据还不能证明这个问题的影响 | 三季报披露后，「这次财报是否改变了判断」就会成为高频场景（路线图第 1 节的目标场景），到时每次重研都会从零开始，产出平行快照 |
| P6 | **判断没有和事后发生的事实对账**（由代码推出） | 只有冻结批次有前瞻收益。报告里也没有可证伪的检查点，下一次研究无从核对上次关注的风险是否兑现 | 积累下来的是文本，不是经过对照的经验 |
| P7 | **跨公司经验沉淀依赖手动纠错** | 「纠错 → `methods` → 跨公司检索」现在只有 2 条方法，因为纠错本来就做得少。路线图第 4 节要求方法必须经过核查后才能生效，这个门槛是有意设的 | 日常研究不会自然产生可复用的方法；但为此绕过核查门槛会带入未经验证的泛化 |

熵增的根因是：每次研究的输出不进入下一次研究（P5），也不和后来的事实对账（P6）。P2、P3、P4 是表面症状。P7 本批不用自动化去解决，而是让 P6 的对账结果成为纠错和评估案例的来源（K3）。

## 2 设计原则

- 不新建知识库、向量库、笔记或「已阅/关注」状态。路线图第 6 节和 PRODUCT.md 都明确排除了这些，积累只靠串联已有的报告、财务表和行情。
- 不改写、不删除历史报告。`body` 受 `body_sha256` 完整性约束，派生信息另行计算。
- 来源分组、过期判断、财务差值和收益计算全部由确定性程序完成。模型只负责写检查点和更新旧风险的状态。
- 研究结论只判断「是否值得继续研究」（[项目契约](project-contract.md)第 2 节），不是买卖评级。所以对账以基本面事实为主，价格只作辅助观察，也不按结论档位统计股价胜率。
- 不营造交易紧迫感，任何页面都不显示研究后的涨跌。

## 3 方案

### K1 首页降噪与过期标记（针对 P1 前半、P2、P4）

**来源分组**：一家公司只要有至少一份「非批次、非重放」的报告，就算「我的研究」，在首页列出。判断条件是 `COALESCE(u.request_id, '') NOT LIKE 'batch-%'`；CLI 发起的任务 `request_id` 为 NULL，不用 COALESCE 会被误判为批次产物。只被初筛深挖过的公司不在首页逐家列出，只显示一行「初筛深挖过 N 家，见各批次」并链到 `/batches`。

首页展示的仍是该公司最新一份非重放报告，批次产生的也算，这样和公司页保持一致；如果最新一份来自批次，加注「来自初筛」。分组完全由来源推导，不需要用户标记。

**过期标记**：取截至今天已过法定截止日的最新报告期，称为「应已披露期」。一季报 4-30、半年报 8-31、三季报 10-31、年报次年 4-30 截止。报告的 `period` 早于应已披露期时，标注「资料已过期：应已披露 2026 三季报」，否则不加标记。

只设「过期」一种状态，不在披露窗口内提前给弱提示。原因是 1–4 月三季报报告会连续四个月处于窗口内，3 月底刚出的年报研究 4 月初也会马上进入窗口，频繁提示本身就是噪音。规则只依赖日期，web 不需要行情凭据。提前披露的公司在截止日前不会被标注，这是有意接受的漏报。

**查询瘦身**：`latest_reports()` 只取列表要用的列，不读 `body`。暂不分页，等真实列表超过约 100 家再加。

**涉及**：`web.py`（`latest_reports`、`home_page`）、`templates/home.html`、过期规则函数及其测试。

### K2 接续研究与检查点（针对 P5、P6，并为 P3 提供列表上的区分信息）

**检查点**：报告新增 `checkpoints` 段，格式为 `[{"text": ..., "cites": [...]}]`，写 1–3 条「下一期披露中应观察的指标与方向，出现什么情况会削弱当前判断」。

检查点是前瞻条件，原文不可能支持一个对未来的判断，所以核验和复核按这样的口径进行：
- 数字核验只核对基期事实。检查点中的数字必须出现在所引出处里，可以是原文、`T.*` 财务行，也可以是 `C.*` 程序计算行。不能凭空写一个出处里没有的阈值。
- 复核只检查基期事实是否正确、观察条件和判断是否相关，不要求原文证明未来方向。这条要写进 `RULES` 和 `review()` 的检查说明。
- 报告未通过复核时，检查点不进入 `facts` 回退展示。前瞻条件离开完整报告后没有依托。

**接续上下文**：用户没有指定父报告时，`_research_context()` 额外带入同一家公司最近一份「通过复核、非重放、非纠错」的报告，但只带它的 `risks`、`checkpoints`、`gaps`、`period` 和 `market_date`，**不带 `verdict` 和 `summary`**，避免把旧结论当成起点。这些内容统一标为「待复核的旧风险与检查点」。

现有 `RULES` 已经要求风险段「结合新旧披露，区分仍存在、已缓解和待核实的风险」。有旧报告时，进一步要求逐条说明旧风险和旧检查点在本期的状态：仍存在、已缓解、已证伪或无法判断，事实一律引用本次材料。这部分写在现有的 `risks` 段里，**不新增 `changes` 字段**。

**确定性差值**：程序比较新旧两份报告的 `table`，算出两次研究之间新增了哪些报告期，以及核心 `T.*`、`M.*`（PE、PB、股息率）的变化。结果作为程序事实放进接续上下文，同时显示在公司页最新报告的上方，作为「自上次研究以来」的一小块。只列数字，不写评价。

**列表展示**：K1 的首页在结论词旁边展示最新报告的第一条检查点，作为主要的区分信息。

**涉及**（逐处列出，避免漏改）：
- `research.py`：`SCHEMA`、`output_schema()`、`RULES`、`SECTIONS` 的使用处、`check()`、`review()` 的检查说明、`repair()`、`_verified_facts()` 的位置正则（不认识的位置会让整份 `facts` 被丢弃）、`_research_context()` 的查询（加上非重放、非纠错条件，并选出带入的字段）、`execute()` 组装 `body`
- 重放：快照中冻结的 `context` 保持原样，状态说明的要求以快照里有没有旧报告为准，不以当前库为准
- `service.py`：纠错位置正则（不加 `checkpoints` 会返回 422）
- `web.py`：纠错位置标签、公司页的差值块
- `templates/report.html`、`stock.html`、`home.html`
- API research-v1 信封：只新增字段，按[项目契约](project-contract.md)第 6 节验证 Skills 消费端
- `screening._report_digest()`：本批不纳入新字段，保持跨公司比较的输入不变

### K3 离线对账复盘（针对 P6、P7）

**不建表、不加 worker 任务、不加页面。** 基准价可以随时用 `market_date` 和 TuShare 历史行情复算，提前记录没有好处。最早一批 6 个月区间在 2027-04 前后到期；首批前瞻批次在同一时期成熟，可以一起复盘。

到时写一个只读 CLI，每季度运行一次，输出放在仓库外的证据目录，内容分三部分：

1. **检查点兑现**（主体）。对每份带检查点的报告，列出之后已经披露的定期报告期，以及对应 `T.*` 指标的实际值。检查点本身是文字，判断兑现与否由人或 Agent 阅读，程序只负责把「当时的条件」和「后来的数」放在一起。
2. **价格观察**（辅助）。只算 6、12 个月相对全收益基准的超额收益，**不按结论档位汇总胜率**。主动研究和批次深挖分开列，批次已经有自己的组合跟踪；纠错和局部追问报告不计入。同一公司在同一自然月只计最后一份。`market_date` 早于研究日期时注明相差几天。
3. **转化**。检查点落空、或判断被事实明显推翻的案例，列为「建议纠错或纳入评估集」的候选，由用户决定是否发起纠错。纠错通过后，经验就沿现有通道沉淀为 `methods`。这是 P7 在不绕过核查门槛前提下的来源补充。

### K4 存储保留（针对 P1 后半）

- 部署备份：每次经授权清理时只保留最近 3 份。删除生产数据目录中的文件属于「删除数据」，**每次执行都需要当次授权**。
- `calls` 与 PDF：**不清理**。`calls.identity` 用于报告运行身份，PDF 是引文的可追溯来源。
- 探索阶段每轮全量存消息，导致 `calls` 偏大（见 P1）。可以改为增量记录，但会改变调用记录的结构，而这些记录用于审计。按目前增速一年内没有磁盘压力，**本批不改**；磁盘余量低于 10G 时再评估。

## 4 分阶段与验收

| 阶段 | 交付 | 验收 |
|---|---|---|
| K1 | 来源分组、过期标记、查询瘦身 | 用生产库真实数据写少量测试，覆盖：`request_id` 为 NULL、批次公司又被主动研究、最新一份是批次报告、年报与一季报同为 4-30 截止、三季报跨年。本机开发实例接生产库副本，在 390×844 尺寸走一遍首页、公司页、批次页；只重建 web |
| K2 | 检查点、接续上下文、确定性差值 | ① 改动影响全局成文契约，按 AGENTS.md 对 11 家固定材料做一次重放评估，确认检查点格式、核验和复核通过率没有回退。重放材料里没有接续上下文，所以这一步只检验基础契约。② 接续验证用三季报披露后的真实案例，选 2 家已有旧报告、且旧风险在三季报中已有明确变化的公司（候选：东方电缆旧报告指出上半年经营现金流为负；紫金矿业），同一天各跑一次带接续和不带接续。比较的不是结论是否一致，而是不带接续时发现的新风险，在带接续时有没有被遗漏，用来检测注意力是否被旧议程占用；同时核对旧风险的状态说明是否有本期证据。③ 加 1 家没有旧报告的正常案例。④ Skills 端读一次含新字段的报告。⑤ 手机走一遍报告页和公司页 |
| K3 | 离线对账 CLI | 2027-04 前后首次运行时，抽 3 份报告逐项核对实际值与 TuShare 原始数据；输出存入证据目录 |
| K4 | 部署流程文档写入保留规则 | 下次授权清理时，先列出要删除的文件，经确认后执行；完整性巡检通过 |

顺序是 K1 → K2 → K4 → K3。K1 改动小，不碰研究契约，可以先上线。K2 等三季报披露完、有真实的「新财报改变了什么」场景再验收。K4 跟随下次部署。K3 等样本到期。每个阶段达到验收即停止扩展。

## 5 本批不做

| 不做 | 原因 |
|---|---|
| 独立知识库、向量库、笔记、已阅或关注状态 | 路线图第 6 节、PRODUCT.md 明确排除 |
| 修改三档结论的定义或提示词 | 原因未查明（见 P3）。改定义会同时影响批次「可选」规则和 Skills 端的解释，需要单独立项，并且要包含探索阶段的评估，不能只做成文重放 |
| 按结论档位统计股价胜率，或在任何页面显示研究后涨跌 | 结论不是买卖评级。单个批次的样本处在同一时间截面，不独立，汇总会被误读为预测力，并诱发以短期股价评价研究质量 |
| 新增 `changes` 字段 | 用现有 `risks` 段的状态说明承载，少改一个顶层契约 |
| 自动从日常研究生成 `methods` | 绕过路线图第 4 节的核查门槛；改由 K3 输出纠错候选 |
| 用人为构造的旧报告做反事实锚定测试 | AGENTS.md 规定不造合成数据；改用旧风险已被新披露改变的真实案例 |
| 关联真实持仓或交易记录 | 账户事实归 `a-stock-agent-skills`（[项目契约](project-contract.md)第 2 节） |
| 删除或改写历史报告、清理 `calls` 与 PDF | 属于证据，并受完整性约束 |

## 6 审查记录

2026-10-27 由 AGY（Gemini 4 Argon High）做只读对抗审查，原文与提示词保存在 `~/.local/share/a-share-research-evaluations/accumulation-review-20261027/`。逐条核对代码和数据后，处理如下：

| 审查意见 | 处理 |
|---|---|
| 按结论档位对账股价，混淆了研究分流和买卖评级，诱发结果偏差；单个批次的样本处在同一时间截面，不独立 | 采纳。不做档位胜率；对账以检查点为主，价格只作辅助并分来源列出 |
| 基准价随时可以复算，提前建表、加 worker 任务和页面，在 2027 年前全是空页 | 采纳，改为到期后的离线 CLI（K3） |
| 接续时带入旧 `verdict` 会造成锚定；新增 `changes` 字段改动面过大 | 采纳。不带结论和摘要；用 `risks` 段的状态说明，不加 `changes` |
| 检查点与复核的「原文支持」规则冲突，会退化成套话 | 采纳。写明前瞻条件的核验口径，允许引用 `C.*` |
| 补上新旧财务表的确定性差值 | 采纳（K2） |
| CLI 任务的 `request_id` 为 NULL，导致分组被误判；漏列 `service.py` 和 `_verified_facts()` 的位置正则；接续查询未排除重放和纠错报告 | 已核实并采纳（K1、K2 的涉及清单） |
| 过期规则在年报/一季报共用截止日和三季报跨年时提示过多 | 采纳，只保留「已过期」一种状态 |
| P5 的例子是开发验收，不是真实使用；结论校准没有覆盖探索阶段 | 采纳，诊断改为标明依据类型，P3 改为「原因未查明」 |
| P7 没有对应措施 | 部分采纳。不做自动沉淀，以免绕过核查门槛；改由 K3 输出纠错候选 |
| 用人为构造的相反旧结论做锚定测试 | 不采纳：违反「不造合成数据」。改用真实案例，比较新风险是否被遗漏 |
| `calls` 改为增量记录 | 暂不采纳：会改变审计记录的结构，目前磁盘余量充足 |
| 备份保留规则过于复杂 | 采纳，简化为保留最近 3 份 |
