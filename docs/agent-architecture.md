## 0. 要解决的问题与成功判据

要解决的不是单次研究快几十秒，而是四件反复发生的事：

1. 每次重构后都要再治理一轮：政策重新激活、部署记录、冻结窗口协调；
2. 重构后性能悄悄退化，要靠下一轮全仓库审查才发现；
3. 模型行为一变，适配就落进业务代码和判断契约；
4. 代码、测试、文档持续膨胀，熵增大于功能增长。

判据（阶段末逐项核对）：

| 判据 | 现状 | 目标 |
|---|---|---|
| 行为不变的代码改动触发政策重新激活 | 触及 policy 依赖链就触发，已激活 30 次 | 0 次 |
| 读取入口的性能退化在发布前被测试拦下 | 少数测试钉住了个别查询次数，没有覆盖到每个入口 | 每个 Web 页面和 MCP 读取工具都有 SQL 语句预算；评估集每次运行输出调用数和各阶段耗时报表 |
| 适配新模型行为要改的 Python 业务代码 | 模型和档位已能用 `MODEL_*` 配置，但适配补丁（如 Gemini 无工具轮仍调工具）写在 `research_tools`、`limits`、`research` 里 | 0 行，适配只落在 L3 与模型配置档 |
| Python 中的研究编排代码 | `Acquisition` 循环、review/repair 往返、`model.py`、`pi_infer.mjs`、`limits.py` | 全部删除（规模为估算，不作硬指标） |

## 1. 诊断

### 1.1 时间花在模型上
11-10 起 25 次成功研究平均 323 秒，其中模型 305 秒（94%）。按阶段：成文 152 秒，工具轮约 6 轮 73 秒，复核 1.2 次 62 秒，修补 17 秒，非模型 19 秒。这些数用作 S1 基线，S4 时复测。

### 1.2 治理成本来自四个结构性耦合
1. **政策身份绑定字节**：`policy/identity.py` 对 policy 包整个 import 依赖链加 `uv.lock` 运行时部分算哈希。共享代码的纯重构也会产生新身份。
2. **性能守护零散**：已有测试钉住个别查询（如 `test_overview.py`、`test_content_search.py`、`test_tools_service.py`、`test_scans.py`）和修补调用次数（`test_repair.py`），但没有覆盖每个入口的预算，新入口和重构后的入口都不受约束。
3. **测试钉实现**：tests 共 14.4 万行，11 月净增约 11.4 万行，相当一部分断言内部路径。
4. **模型适配混在业务里**：探索循环、停止判据、上限、格式纠正与复核往返都由 Python 手写，research 核心四个文件 10 月以来改了 103 次，`limits.py` 注释里记着针对模型行为打的补丁。账本规则本身已集中在 `ReviewLedger`，`merge_repair_patch` 也已是纯函数：问题不在 L0 规则，而在编排与规则之间缺少跨进程的持久状态和事务边界。

## 2. 目标架构：按变化速度分层

原则：快变的层不能拖着慢变的层一起变。层间只通过稳定接口交互。

```
L3 Agent 层（最快，可整层替换）  agent-runner：TypeScript + pi-durable
      │ 内网 MCP（run/角色/阶段绑定凭据）
L2 研究能力面                     由 worker 托管的研究 MCP 端点
L1 作业编排（Python worker）      受理、原子领取、run 状态、预算账、审计、发布门禁、记分
L0 事实与规则（最慢）             材料与证据写入、核验、ReviewLedger、补丁合并、判断账本、账户、政策
      裁判：评估集 + 同材料稳定性测量 + 政策语料回放
```

### 2.1 L0：规则不动，补上持久状态与事务
- 保留：`material.py`、`checking.py`、`ResearchTools` 的取证与计算实现、`calculate`/`valuation`、`ReviewLedger`、`merge_repair_patch`、判断账本、账户与政策。
- **每个 run 的材料只由 Python 写**：每次工具调用带稳定调用 ID（L3 在发起外部调用前用 `api.memo` 持久化，重放时沿用同一 ID，见 README《Tools that park》）、参数摘要和预期材料版本。工具的变更与原回执**同一事务**写入 `run_tool_calls`。同 ID 重送直接返回原回执；材料版本不符时报可操作的错误；同一 run 的并发写串行分配 `C.n`、来源编号等证据编号。这样 L3 重放工具调用不会重复取数或改写证据。pi-durable 的 `replay: "safe"` 只表示“中断后允许再执行”，安全性由这里的幂等保证。
- **历史 `--replay`** 使用单独的只读工具集：禁止新取证，校验冻结快照哈希与公司，验收最终材料哈希不变（保持 `research.py` 现有语义）。
- **ReviewLedger 持久化**：每个 run 的账本状态存 `app.db`，每轮复核仍绑定草稿与材料哈希，整轮验证通过才提交。

### 2.2 L2：研究能力面
- **端点宿主**：由 worker 进程托管研究 MCP 端点，挂在新的私有网络 `research-net` 上，只有 agent-runner 能访问。worker 持有 TuShare 凭据和 run 材料写权限；agent-runner 只持模型凭据。凭据分工从“worker 两者都有”变成各持一类。
- **凭据**：L1 为每个 run 的每个角色签发短期凭据，绑定 `run_id`、角色（researcher / reviewer）和阶段（acquire / draft / review / patch）。服务端对**每次调用**校验这三项与 L1 中的 run 状态。只给模型看的工具清单（`modelTools`）只是展示，不当权限用。
- **工具集**：
  - 研究员：现有取证与计算工具（取证阶段；修补阶段恢复现有受限补证工具 `REPAIR_TOOLS`，按剩余额度）、`submit_draft`、`submit_patch`（带原稿版本，复用 `merge_repair_patch`；非法补丁走现有“整稿重写”路径，次数有上限）、`rebut_issue`（据证反驳）。
  - 复核员：只读材料与草稿、`review_pending`（读本轮待办）、`review_decide`（一次提交整轮完整决议，由 `ReviewLedger` 原子校验：旧问题与被删改风险各恰好决议一次、核验出处与新版去向、程序分配新问题 ID）。
  - 两个角色都没有账户、政策、发布工具。
- **验收用例**（S3 必过）：研究员调用 `review_decide`、复核员调用 `submit_patch`、跨 run 访问、研究凭据调用公网账户工具，四种情况都要被拒；同 ID 重送返回原结果；Python 已提交但回执丢失后重送，不产生第二个 `C.n`。
- **兼容**：研究能力面只对 L3 内部开放，工具与调用方随同一提交修改，不设旧名保留期。对外账户与政策工具面沿用双入口方案的规则。

### 2.3 L3：agent-runner（pi-durable）
- 新目录 `agent-runner/`，Node 22，独立镜像和容器，精确锁定 `@earendil-works/pi-durable`、`pi-ai`、`chord`、`pi-mcp` 版本。MCP 连接用 `pi-mcp`（官方独立 MCP 客户端），加一个桥接扩展把研究能力面注册成 Harness 工具；两个角色**各自显式安装**自己的扩展，不继承父配置。
- **存储与会话**：一个 `agent.db`，一个写入 Harness；每个 run 有独立的研究员与复核员对话。内部键 = 库实例 ID + `runs.id`（CLI、评估集、历史重放的 run 可能没有 `request_id`）。对话 ID、submission ID、输入摘要和终态写入 `app.db` 的 `run_agent` 表。
- **不装**：CodingTools（read/write/edit/bash）、code mode、`env`、压缩（compaction）。内置命令与文件能力因此不存在；MCP 桥接扩展属于受信任的宿主代码，纳入代码审查。
- **重试口径**：保留现行 `maxRetries: 0`，由 L1 的失败分类决定是否重排。`sessionId` 改为按对话持久的 UUID，S4 实测提示缓存命中率与 429 表现后定稿。

**流程映射**

| 现在 | 之后 |
|---|---|
| `Acquisition` 探索循环 | 研究员对话的回合循环 |
| 连续两轮无增量即停（重复计算和仅换名的查询不计增量），停后留一次无工具成稿 | 增量判定仍由 L0 计算，每次工具回执附带增量计数；判定停止后，L1 把该 run 的阶段切到 draft，取证工具开始返回“取证已结束，请成稿”，同时按 README《Per-Conversation Agent》用 `configure` 把研究员工具集切成只含 `submit_draft`（从下一次准备请求起生效，当轮已发出的取证调用由服务端按阶段拒绝）。不用 `afterTools` 的 `terminate`，因为它会直接结束整次运行 |
| 30/21 次调用、单次 600 秒、整体 1800 秒、共享取证 1200 秒、修补与成稿预留 | **run 级预算账在 L1**，跨两个角色持久计数。闸门放在**实际发送入口**：runner 用一层 provider 包装替换直连发送，先调用 L1 的 `attempt_begin`（登记 attempt ID、阶段、实际请求、模型参数并扣预算），提交成功才把请求交给真实 provider；拒绝或登记失败都返回错误结果，不出站。不用 `beforeProviderRequest` 做闸门，因为钩子抛错只会被上报并跳过（README《Errors》）。L1 到时对该 run 的研究员和复核员两个对话分别 `abortTask`，等两者都空闲后再写终态。预留额度由 L1 按阶段保留 |
| 成文后机械检查 → 独立复核 → 最多修正两次 | 研究员调用 `submit_draft`：L0 做机械检查；通过后 L1 向复核员对话提交复核任务，`submit_draft` 按 README《Tools that park》挂起，等复核结果以信号送回，再把问题列表作为工具结果返回研究员。复核轮数上限由 L1 控制。复核员格式无效时，沿用现有“说明原因、当轮可纠正一次” |
| 可交付条件 | 只在 L1 发布门禁判定：已复核终稿中定位合规的具名 `question` 可以交付，其余未解决问题一律阻断；失败稿只保留已复核且能安全定位的事实。估值、立场冻结、事件证据、报告与 run 终态同一事务写入 |
| `model.py` 每次起 Node 进程 | 常驻进程，模型目录与凭据只初始化一次，保留离线模型解析、扩展来源哈希、拒绝带工具的 provider 扩展 |
| `FAILURES` 封闭词表 | provider 边界的 `attempt_end`（`afterResponse` 钩子与中断处理）记录具体原因：超时、长度截断、空输出、provider 错误。L1 保留“失败且有报告”和“中断且无报告”两种交付形态，以及阶段、已取材料和脱敏错误。范围外、来源输入、运行上限、成文格式、引文计算、复核格式、实质复核等运行失败分类不变 |

**审计**：`calls` 表的行在请求发出**之前**由 `attempt_begin` 写入（`step`、时间、实际模型与参数、完整提示，或可逐字还原的 `prompt_base` + `prompt_block`，以及 `prompt_sha256`），由 `attempt_end` 补全响应、用量、耗时或脱敏错误；崩溃时行保持开放、用量为空。运行中计数、`stability.py` 依赖的 `step` 与 `identity.actual.model` 口径不变。`agent.db` 只是工作记忆；runner 只删除导入已确认、超过 30 天的会话。

**并发与幂等**：L1 原子领取最多 2 个 run（`runs.status` 条件更新）。重启时先按 `run_agent` 找回原会话；已终止的月批要取消在途工作，并拒绝迟到的结果。S4 必过的故障用例：受理回执丢失、结果导入后发布前崩溃，各只产生一份报告；已终止月批中的在途 run 重启后不产生报告。

**其他模型调用入口**：Q20 选股、强制排序、S10 独立比较目前直接调用 `model.complete`，改为调用 runner 的单轮无工具任务接口，保留各自的格式修正、调用明细、冻结规则，以及“三项比较或排序各最多 2 次、整批最多 636 次”。这些任务没有单股 run（`calls.run_id` 非空），attempt 键用“批次 ID + 任务名 + 次序”，明细写回批次现有记录位置。双角色预检（worker 启动与部署就绪检查）改为调用 runner 的 `/preflight`。

**可替换性**：L3 对下层的全部依赖 = 研究 MCP 能力面 + `attempt_begin`/`attempt_end` + 单轮任务接口 + `run_agent` 约定。更换 harness 只重写 L3。

### 2.4 L1：作业编排
受理、去重、材料冻结、原子领取、run 状态与阶段、预算账、审计、发布门禁、记分、月批与扫描调度都在 L1。入口逐一迁移并分别验收：
- 单家研究、纠错和反馈重试；
- 扫描接续：同公司事件合单、每日最多 5 个接续 run、发布时按终稿回写每个事件的证据；
- 月批：排除自动前序和扫描事件，按批次创建时间冻结方法目录；
- 历史诊断：worker 现在不领取 `diagnostic`（`test_diagnostic_isolation.py`），本方案不恢复诊断调度，只保证历史诊断按 ID 可读、排除在正式记分之外。

### 2.5 模型配置档
配置档（JSON，入库，哈希写进每个 run 的 identity）：每个角色的 provider、model、reasoning、max_tokens、各项上限与预留、复核轮数上限、提示变体 ID、并发数。现有 `MODEL_*`、`MODEL_REVIEW_*` 环境变量并入配置档后删除。上限数值保留一行来源说明，沿用 `limits.py` 注释的做法，不另建逐行台账。

换模型（E 类）= 新配置档 + 评估集全集 + 同材料稳定性对照 + 新旧同材料对照。

### 2.6 判断契约与编排身份
- 契约面清单改成机器可读：TS 提示、角色工具集与工具定义、Python 冻结规则，各取语义哈希。`test_judgment_contract.py` 改为从这份清单构造，不再读 `compose`/`review` 等 Python 源码。
- 契约号按实际发布顺序依次递增，不预先占号。S5 改变契约面，取当时的下一号；12-18 的股息率交叉验证与 PB 同期检查写在 L0 核验里（S5 后保留），若先于 S5 发布则单独取号；段 4b 在 S5 之后取下一号，日期 12-23 不变，直接在新结构上实现。4b 的持仓快照必须在**受理并创建 run 的同一事务**里冻结。
- run identity 增加编排身份（runner 镜像摘要 + 配置档哈希）。`stability.py` 与记分读取器按它分组；旧记录标“未记录”。

## 3. 政策身份绑定行为

### 3.1 身份
身份 = 完整元组（规则文件、指南、参数、语料清单哈希、输出指纹）的摘要。比较时逐项给出差异：只改指南（如治理红线只写在指南里，不影响任何样本输出）会表现为“仅指南变化”，身份照样改变。代码文件和 `uv.lock` 不进身份。

### 3.2 语料与回放
- 按实际评估类型分派回放：每条样本带原有参数、时钟、上一通知状态和父回执（定仓、情景要引用父监控回执），样本顺序固定，输出规范化。
- 来源：`policy_evaluations` 的 520 行，按类型去重抽样。现有分布严重偏向止损检查，需要在真实样本上做最小的、显式标记的变体补齐，至少覆盖：交易时段边界、行情新鲜度 900 秒两侧、参数到期、空仓与有仓、相同告警去重、被拒请求（这类请求通常没有评估行）。
- 采集端：用冻结的原始输入回放到 bundle，覆盖依赖升级改变原始数据解释的情况。
- 互变测试：逐条列出“哪条可执行规则由哪个样本检出”；指南专属规则验正文。S2 的结论只覆盖明列的可观测行为。

### 3.3 运行时核验
候选镜像在发布时以禁网、语料只读挂载的方式回放语料，生成与**镜像摘要绑定**的核验记录（单独一步，时限在 S2 实测后确定，不挤进现有 40 秒的身份构建）。运行中的 worker 和 tools 在评估前核对：自己的镜像摘要有一条与生效身份匹配的核验记录。取代现在“监控前后检查当前安装的代码哈希”。

### 3.4 兼容与回退基线
- 清单升为 v3。S2b 删除为新政策生成 v1/v2 身份的代码，但**保留对已登记 v1/v2 清单的只读验签与重算**：只用于核对历史身份、恢复前驱政策，不为新政策生成。
- 旧镜像的验证器只认 v1/v2，而完整性检查（`registry.inspect`）会遍历所有已登记版本，所以 v3 清单一旦登记，不能读 v3 的镜像就无法接回生产。v2 身份按 `a_share_research/policy/` 的 import 闭包与运行时锁的实际字节计算，任何改动这条闭包的镜像都重现不了前驱身份。因此 S2 分两次发布：
  - **S2a（11-28，月批冻结前）**：只加入 v3 清单的读取与验签，不生成 v3，不加库迁移。闭包改变，按例行发布由常设 owner 凭据自动激活最后一个 v2 身份（激活 31）；回退目标是当前生产镜像，此时账本里还没有 v3 清单，旧镜像可以读。
  - **S2b（12-05）**：改为生成 v3，以 v3 重新登记现行政策（规则、指南、参数与激活 31 相同）。恢复镜像是 S2a 镜像：它能读 v3，也能用自身文件重现激活 31 的 v2 身份，满足部署恢复预检（`deploy.py:424`）。镜像核验记录写入发布证据目录与 `release-state.json`，不写入数据库，因此 S2a、S2b 都不需要迁移。
- 回退规则：**不带库迁移的发布，回退到紧邻的上一个生产镜像**。**带库迁移的发布**，回退探针要求库版本相等（`rollback_probe.py:35`），所以发布前构建一个恢复镜像：前驱提交只加上本次迁移，其余代码不动。用它在迁移后的库副本上走通回退，再经发布入口指定为本次回退目标。现有的恢复镜像参数 `--initial-recovery` 只限首次纳入 tools（`deploy.py:705`），S3 把它改成带迁移发布通用的恢复镜像参数（`deploy.py:743` 已按它选择回退镜像），12-11 删除首次发布路径时不删这部分。S2b 之后身份按行为计算，加迁移不会改变恢复镜像的政策身份，只需在构建时为它生成核验记录。
- 本方案的库迁移集中在 S3。S4、S5 不加迁移；确实需要时按上一条处理。由此得到各次发布的回退目标：S3 回退到“S2b 加 S3 迁移”的恢复镜像；段 4a（12-18）回退到 S3 镜像；S5 回退到 4a 镜像；4b 回退到 S5 镜像，若 4b 带迁移，也按上一条构建恢复镜像。
- S2b 发布前在生产副本上分别构造三种状态：“已登记未激活”“已激活”“激活成功但回执丢失”，验证 S2a 镜像作为恢复镜像能读全账本、恢复前驱政策（激活 31）并重新受理。

## 4. 性能预算

- 生产库快照放证据目录。预算测试单设一个目标，由发布入口执行；快照缺失时**失败**，不跳过。
- 每个 Web 页面与 MCP 读取工具：SQL 语句数上限（`set_trace_callback`，扩展现有测试的写法）；关键页面耗时上限取实测值的 2 倍。
- 研究：评估集每次运行自动输出每家的调用数、各阶段耗时和 token，与同配置上一次对比，作为退化线索，不作硬门。
- 调高预算须在同一提交里写明原因；入口退役时，它的预算随之删除。
