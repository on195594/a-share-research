# 分层重构：设计取舍与复盘

两步于 2026-11-21 上线：第 1 步 `4881ad1`（政策身份与发布瘦身），第 2 步 `5d92b5b`（切换到 agent-runner，并删除旧编排）。现行进程与接口见[系统架构](../ARCHITECTURE.md#研究与模型调用)，部署与回退约束见[实施计划](implementation-plan.md#当前部署)。本文只记录读代码看不出的取舍和复盘。方案 v1–v6、Codex 与 agy 的审查记录存放在证据目录 `~/.local/share/a-share-research-evaluations/architecture-plan-20261121/`。

## 1 要解决的问题

要解决的不是单次研究快几十秒，而是四件反复发生的事：

1. 共享代码的纯重构也会产生新的政策身份。身份原先对 policy 包整条 import 依赖链和 `uv.lock` 算哈希，到 11-21 已重新激活 30 次。
2. 性能退化没人看见，要等下一轮全仓库审查才发现。
3. 模型适配逻辑混在业务代码里。探索循环、停止判据、上限和复核往返都由 Python 手写，research 核心四个文件 10 月以来改了 103 次。
4. 代码、测试和文档持续膨胀。

诊断时的耗时数据：11-10 以来 25 次成功研究平均 323 秒，其中模型占 305 秒，即 94%。所以本次不以提速为目标。

## 2 分层与取舍

| 层 | 位置 | 职责 |
|---|---|---|
| 事实与规则 | `core/`、`checking.py`、`drafts.py`、`reviewing.py`、`account/`、`policy/` | 材料与证据、引文核验、`calculate`/`valuation`、补丁合并、复核账本、账户、政策 |
| worker | `research.py`、`research_mcp.py`、`prompts.py`、`runner_process.py` | 受理、材料冻结、工具执行、机械检查、全部提示词、复核与修补的流程决定、发布门禁、调用审计 |
| agent-runner | `agent-runner/*.ts`、[模型配置档](../a_share_research/model_profile.json) | 各角色的 Agent 循环、工具集切换、无增量停止、调用与时间上限、调用记账上报 |

所有者定的原则：不为旧逻辑和旧数据做兼容层，发布一律从简，允许试错；切换后不保留新旧两条路径，出问题就前向修复，或回到上一个提交。系统边界（用户输入、外部 API、模型输出解析）照常校验。

- **pi-agent-core，从宿主的 pi 安装加载。** runner 按宿主 `current-version` 动态加载 pi-agent-core、pi-ai、pi-mcp，以及 pi-coding-agent 的 `ModelRuntime`（负责凭据和 OAuth 刷新），不在仓库锁版本，随宿主升级。`calls` 记录 `pi_version`，版本变化后行为异常时先对照版本。没选 pi-durable：它的崩溃续跑对约 5 分钟的研究没有必要，还要单独锁版本。也没在 pi-ai 上手写循环，那等于继续自己维护适配代码。
- **runner 用 Node 24 直接运行 `.ts`。** 不加构建步骤和 npm 依赖；worker 镜像的 Node 与宿主保持同一主版本。
- **MCP 跑在子进程的 stdio 上。** 每个 run 启动一个 runner 子进程，worker 在它的标准输入输出上提供本次研究的 MCP 服务。这样不用端口、线程和令牌，worker 仍单线程、一次只跑一个 run，材料不需要加锁。工具 schema 只在 Python 定义一次。
- **提示词和流程决定只在 worker 一处。** 运行时提示词全部由 worker 生成，下一步是复核、修补还是结束，也由 worker 的回执决定；runner 只负责转发（`9de8429`）。代价是改提示词仍要改 Python，按 D 类验证。之所以不把措辞放进 runner，是因为迁移时提示词被改写过一次，见第 3 节。
- **修补另开一段干净对话。** 输入是索引化原稿、刷新后的资料和问题列表，不在研究员的长对话里续写，否则会一直带着 6–15 轮工具回执和旧稿全文。
- **致命错误不交给模型。** 来源身份或已读页冲突这类错误由 worker 记下失败分类，然后直接结束子进程，不作为可纠正的工具结果返回。
- **模型配置档取代 `MODEL_*` 环境变量。** 角色、模型、档位、上限及每项上限的依据都写在一份 JSON 里，随代码发布。它的哈希和提交号写入每个 run 的 identity，记分按配置档分组。换模型（E 类）就是换一份配置档，再跑评估集。
- **判断契约只剩 `JUDGMENT_CONTRACT` 整数**，口径有实质变化时手动加 1，不再锁定源码哈希。
- **政策身份 = 规则 + 指南 + 参数。** 代码和 `uv.lock` 不再计入身份，运行时也不再比对代码字节。旧版本行作为历史留在库里，不再验签。改 `policy/` 代码时，用真实评估样本写成的 pytest 兜底。
- **发布只保留必要步骤：** 空闲检查与暂停、备份、切换镜像、就绪检查、政策身份变化时自动激活、清理旧镜像。回退探针、首次发布路径和 `--complete-held` 全部删除。回退就是重新发布上一个提交的镜像；带库迁移的发布，先恢复发布前备份。

### 问题与教训

1. **迁移时提示词被改写。** 把提示词搬进 runner 时，Codex 顺手压缩了探索、复核、修补三段，复核清单从 8 条只剩 3 行。结果 5 家里有 2 家核查失败，而生产同期是 3/44。逐字 diff 后才发现。处理办法是改成由 worker 唯一生成（`9de8429`、`071beca`）。以后派发迁移任务，要写明提示词逐字搬运；审查时逐字比对新旧提示词。
2. **合并前审出两处缺陷**（`9c19a79`）：工具调用不受整体截止时间约束，runner 退出时失败原因丢失。两处都在合并前修好。
3. **删模块后有引用漏网。** 按导入路径搜索，没搜到 `tests/test_layering.py` 里的裸字符串 `"limits"`，main 因此失败了 1 项，测试瘦身时才发现（`73d4ea6`）。另有一项 `test_batch_c` 在 main 上早就失败，带着上线，事后才删除（`732dd78`）。以后删模块要用 `git grep -nw <模块名>`；发布前，main 上的已知失败要清零或写明理由。
4. **诊断夸大了测试规模。** 方案写的“14.4 万行测试”把 10.3 万行样本数据也算进去了，实际测试代码是 3.9 万行（`84d84e1` 已更正）。统计测试规模只数代码，样本数据单独报。
5. **方案文档成了最大的过期文档。** 实施细节、API 坑、前置检查和文档对齐表在上线后都已进入代码和提交记录，方案却仍有近 2 万字节，三份文档还重复描述 runner 流程。11-22 已压缩为本文。以后工作包收尾时，在同一次交付里把方案收成“取舍 + 复盘”。
6. **简化后的回退路径已经实际用过。** 11-22 的 `a963462` 发布被检查拦下（fail-closed），随后重新发布 `f57540d`，再发 `2f5e000`，中途不需要专门的回退工具。
