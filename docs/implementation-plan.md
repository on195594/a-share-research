### K2/K3 推进记录

**固定对照条件**：标签 `k2-baseline-20261028` → `f77ed55`；同一生产库快照和 132 份 PDF 保存在 `series-release-20261028-132726/k2-baseline/`。只读核验华东医药、东方电缆自动接续分别命中旧报告 36/37，其他同公司纠错上下文为空；两份旧报告各有 5 条风险、没有检查点，所以②检验旧风险状态，检查点继承与关闭须在③覆盖。剩余实验使用该代码，**每家公司每组各从固定数据库复制独立副本**，不得在同库先跑基线再跑候选，以免基线报告成为候选 prior；不混入 1a/1c。

正式开跑时，两组直接调用 `service.submit()` → `research.execute()`，使用同一非空问题、空 `parent_report_id` 和 `feedback`；基线 request-id 用 `batch-k2-` 前缀关闭自动接续，候选用 `k2-`，保存材料后核对 prior。该前缀只用于隔离实验，不进入 worker/批次流程，不比较列表来源分类。先从实际三季报原文列出每家 3–5 条必查事实，再按[积累方案 K2②③](research-accumulation.md#4-分阶段与验收)执行。

另存探索前的初始材料，比较两组 `table`、`market_date`、公告目录和 `doc.sha256`，记录相同与差异；先确认取数条件可比再解释接续效果。探索阶段补读不同材料属于自主取证结果，不要求最终材料完全相同。每组仅运行一次，结论须说明模型随机性，不能把单次差异直接归因于接续机制。

## 验证与交付规则

| 变更 | 验证 |
|---|---|
| 文档 | 路径、锚点、职责与状态一致，`git diff --check` |
| 确定性代码 | `uv run pytest -q tests`，保留受影响的真实样本回归 |
| 研究流程 | 受影响真实案例 + 1 个正常案例；仅切换模型或全局成文/复核契约时跑一次评估集，见[产品方案第 8 节](proposal.md#8-开发方式) |
| 页面 | 本机真实浏览器、手机尺寸走主流程 |
| 跨项目接口 | 生产者/消费者合同、只读查询无研究副作用、真实 Agent 主流程、失败与回退；Skills 按其 development，Lib 按其 RELEASE_CHECKLIST |

固定材料重放不等于重新取数；历史捕获不证明当前候选。出现失败或新改动才补测，记录采用或拒绝的依据。交付区分代码、测试、发布、客户端激活和生产验收。备份保留与证据清理遵循[积累方案 K4](research-accumulation.md#k4-存储保留针对-p1-后半)，不自动删除。
